Alicore · System Architecture

Four layers, one database, three ways in.

The marketing site is static almost everywhere. What makes the architecture worth drawing is the small set of places it isn't — where a request actually reaches Postgres, and under which key.

Request paths

Where a request reaches the database

Three routes through the same stack. They differ only in the bottom two rows — and that difference is the whole security and performance story.

Timing

The database is also read at build time

This is the part that surprises people. Static pages still show admin-managed photography and project tiles — because astro build queries Supabase and bakes the results into the HTML. That has consequences for how content updates propagate.

Write path

How an enquiry is captured

The most consequential path on the site, and the one with the least obvious shape: the customer's drawing never passes through the Worker.

Data

Every table, and who touches it

Four tables in Postgres, plus Supabase's own auth.users. Row-level security is on for all of them, and no policy grants anonymous access to enquiries — the browser never holds a key that could read one.

Why two keys. The anon key is safe in a browser because row-level security constrains it — it can read published projects and active media, nothing else. The service-role key bypasses RLS entirely, so it is read only inside API routes and admin server-rendering, and never imported into a file that reaches the client bundle.
